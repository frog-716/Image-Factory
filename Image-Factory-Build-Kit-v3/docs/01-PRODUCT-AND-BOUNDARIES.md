# 01 产品目标和系统边界

## 核心模型

系统由“业务意图、持久化流程、能力节点、资产与事实、人工决策、反馈证据”组成。
一次聊天是工作入口之一，无法承担唯一状态来源。

```text
开发期：你 → Sol 高 → Luna 极高子任务 → 集成与验收 → 可运行项目

运行期：
飞书选商品/场景/用途并提交
    ↓
本地 Runtime 读取、校验、冻结、排队
    ↓
Codex 节点：输出结构化创意方案
    ↓
Prompt 编译节点：固定组件版本与变量
    ↓
NativeImage Worker：实际生图并交回文件和证据
    ↓
脚本：校验、合成、文件归档、飞书回写
    ↓
飞书人工审核
    ↓
Runtime 导出批准图片、同步交付状态、处理效果数据
```

Codex 文本规划和图片执行是两个不同能力。可由同一外部程序承载，但接口、预算和验收分开。
运行期不要求使用开发时的 Sol/Luna 组合；节点只要求声明输出契约和已验证能力。

## V1 有意收窄

一个现有飞书 Base、一台 Mac、一个运行器写入者、童鞋、3 个候选、固定可配置顺序流程。
素材和 Prompt 组件可点选；不做任意代码节点、用户自定义脚本执行或无限图结构编辑。
发布的 Workflow 不可原地改写，编辑产生新版本。用户提交后本轮快照固定。
不做通用 Agent 平台、微服务集群、ComfyUI 替代品或第二套账号系统。

## 人与机器的权威

人维护商品事实、权限用途和最终审核。飞书是这些业务资料的主界面。
Runtime 是执行状态的唯一权威；飞书中的运行状态由 Runtime 投影，人工不直接改“已交付”。
Prompt 模板/Workflow 的已发布业务版本在飞书；执行器代码、节点注册表和安全规则在项目中。
图片文件优先复用已跑通的飞书附件链路，本地保留校验缓存和运行快照；不要求用户翻文件夹。
SQLite/事件记录复用现有账本或受控迁移；不让新旧账本同时指挥同一任务。

## 自动化是真进程

飞书自动化只能提交意图或提醒，不能凭空唤醒电脑中的 Codex。
V1 采用本地运行器定期拉取已提交任务，推荐 30 秒起步、单机串行写、遵守实际接口限流。
电脑关机或运行器关闭时不执行；界面显示离线或最后心跳。这里不承诺云端永远在线。
本地自动启动通过后续安装向导显式启用，不默认改 launchd 或系统登录项。

## 两种能力验收标识

L1：Runtime 独立推进，原生图片任务仍需打开执行窗口；透明标明半自动。
L2：经本机验证的 headless 原生 Worker，可由 Runtime 启动，人工只在审核节点介入。
用户目标是 L2。L1 是明确退化状态，不能冒充 V1 自动生图已完成。
