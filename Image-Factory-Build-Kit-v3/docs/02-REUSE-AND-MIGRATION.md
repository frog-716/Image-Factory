本包依据当前对话中的用户报告，以及上传的 `08-FEISHU-PERMISSIONS.md`。
报告中的测试数量、record ID 和成功历史是交接线索，必须在本机读回核实。
没有你电脑上的最新代码快照，禁止假设参考类名就是你当前函数签名。

## B0 盘点输出

`BASELINE.json`：实际项目路径、Git 状态、源码摘要、测试命令/结果、配置字段结构、数据备份位置。
`REUSE-MAP.md`：已有模块 → 保留/包装/增量修改 → 新需求 → 影响测试。
`CAPABILITIES.json`：本机 CLI/模型/原生生图/headless/Subagent/目标模式的实测等级。
`STATUS.json`：开发阶段与验收状态，和业务运行状态分开。
`HANDOFF.md`：下次打开新对话可直接继续，不依赖旧聊天内容。

不得在上述文件中写 token、Cookie、Keychain 内容、完整 CLI 环境或未脱敏 stdout。

## Git 和备份

不是 Git worktree 时：先受控备份源码、现有数据库快照、必要配置和资产引用清单，校验可读。
不要 `git add .`，不要把 `var/`、用户图、日志、凭证加入仓库。
可以提出初始化本地版本管理的最小方案；不设远端、不 push、不重置用户未提交改动。
开发并行使用文件所有权清单；对同一文件、schema、运行数据库、飞书写入全部串行。

## 改表原则

先比对真实 schema，再给 migration dry-run。仅增加无法用现有关系和字段表达的最小字段。
每项变更 journal-before-write、读回验证和断点保存。保留回滚清单。
无需为了 V1 新建十几张表：StepRun/Attempt/快照可先存现役本地账本，并回写运行档案附件。
Demo 审核新语义可需新增“Demo视觉检查”“仅限演示使用”两个布尔字段，范围由任务模式派生。
不可把旧“商品准确/品牌渠道合规”重新解释成演示检查；不可自动迁移旧审批为新有效审批。
新代码使用 review_policy_version 区分；旧任务按旧策略解释，新任务按新策略。

## 历史保护

新 live 验收用独立前缀 `V1-DEMO-KIDS-*`，避免与历史任务冲突。
RUN-003 默认保留为旧待准备证据；迁移需单独明确的快照、版本与关系映射。
RUN-002 状态若修正，需要从既有交付证据派生并记录迁移事件，不凭聊天报告改成完成。
禁止用删除重复记录当默认幂等处理；发现业务键重复先对账，明确来源与依赖后再决定隔离。
