# 01 · 架构与边界

## 核心结论

平台围绕“一次有依据的商品表达”组织。图片数量只是生产量；可追溯、可审核、可恢复、可关联业务结果，才决定这条生产线是否可靠。

每次任务回答四个问题：画的商品是什么；哪些内容允许变化；用什么流程和素材产生；哪个版本被人批准、在哪里使用。

## 分工

| 角色 | 负责 | 不负责 |
|---|---|---|
| 飞书多维表 | 关系数据、商品/素材附件、流程、任务、审核事件和反馈；运营人员维护业务资料 | 审核者手填运行哈希或直接驱动本机生图 |
| Human UI | 本机两页“待我审核／任务与交付”；把人的决定送到 Engine API | 自建业务规则、直接写飞书审核表 |
| Workflow Engine | 唯一业务状态机；校验、冻结、预算、合成、可信审核、归档和 ZIP | 审美、商品真实性判决、原生模型内部调度 |
| Codex | 被 Workflow 调用时承担 AI／原生生图节点，可提供视觉疑点建议 | 长期主控业务流程、保存唯一业务真相、冒充人批准 |
| 人 | 确认商品事实/授权、视觉方案、最终审核、实际发布和指标口径 | 重复复制文件与填写机器能获得的运行信息 |

本版的业务权威在飞书。每次执行以被冻结的快照为输入；本地 SQLite 是执行状态账本，任务运行档案随关键步骤保存到飞书。后续修改飞书业务信息会触发冻结检查，不能悄悄影响已开始任务。

## 图片放在哪里

V1 直接用飞书附件保存商品素材和成图，画册能看，记录能选。Human UI 只补足飞书难以安全完成的看大图、确认审核和领取 ZIP，不另建素材库或业务后台。

本机 `var/live/` 存放临时输入副本、原生输出、执行账本和 ZIP。用户日常不需要翻这些目录。最新运行档案包含恢复所需的输入、冻结请求、已登记输出、回执和审核摘要；它不包含 larkcli 凭证。

这是小规模验证的取舍：关键步骤上传完整检查点，会占用飞书容量和传输量。默认单图 20MB、单个未压缩检查点 128MB、每任务 12 候选。大规模生产时再把高清文件和检查点迁移到对象存储，飞书继续保留可视化入口、关系和缩略图；V1 未实现该适配器。

## 对象关系

```text
商品 1 → N 商品原图版本
素材 N ← N 任务（任务选图及流程步骤选图）
流程 1 → N 顺序步骤；每个流程版本独立记录
商品 1 → N 任务；每个任务固定 1 个商品、1 个流程
任务 1 → N 候选槽位 → N 调用尝试 → 最多 1 个接收成图
成图 1 → N 人工审核事件；最新有效结论决定是否可交付
成图 1 → N 上架记录（具体渠道/账户/版位/时间/广告或页面 ID）
上架记录 1 → N 每日指标版本
```

V1 每个任务只选一个已确认的商品原图角度。多角度商品图分任务处理，避免把鞋面、鞋底和另一颜色混为同一输出依据。已生成成图如需作参考，另建“风格参考/场景参考”记录，保留来源成图说明，不能直接变成商品事实。

## 可视化 Workflow 到底怎么编辑

飞书“流程步骤”表按流程分组、顺序排序。你可以增加多个提示词节点、修改文本模板、给节点关联参考图片。脚本将启用的提示词节点按序组合为一份冻结提示词。节点选的参考图片会汇总到真实工具调用输入列表。

支持的顺序有两种：

```text
多个提示词节点 → 原生生图 → 原图合成 → 文件检查 → 人工审核
多个提示词节点 → 原生参考图编辑 → 文件检查 → 人工审核
```

V1 的一个候选只有一次生图阶段，未实现任意分支、循环、多段图片生成 DAG、拖拽节点画布或可执行代码节点。有限步骤类型能减少 AI 自行解释流程造成的风险；新增节点类型需要实现代码及测试，不能只在表里写一句话就当它已自动化。

## 两种生产方式

**背景合成，默认**：模型只生成背景。脚本用已确认的透明商品原图裁剪透明边界、按固定比例缩放、摆放、合成。记录原图 SHA256、裁剪区域、缩放比例、位置和画布。商品没有被重新描绘，但缩放会改变采样像素，因此不能宣称像素级原样复制。接触阴影、透视和摆放自然度仍需人检查。

**参考图编辑，选配模板**：商品原图和参考图都送入原生工具，允许更自然的场景融合。模型可能改变商品形状、Logo、颜色或结构。脚本只能检查格式、尺寸、来源和回执，不能证明商品忠实度。默认未发布此流程，人工确认风险后才启用。

纯白商品首图可以另建固定白底流程，但各平台当前要求须由运营核实并放入任务约束。不能把通用“场景广告图”流程直接标为所有平台主图合规。

## 不变量

提交时的 SKU、原图、事实版本、流程版本、提示词及素材 SHA256 冻结。新版本永远新增，不覆盖旧成图。

一个槽位派发前必须先记账并写入远端检查点。没有回执时，它表示“可能已执行”，不能自动当作失败重画。重新尝试由人确认可能已消耗额度，再从任务剩余调用次数扣减。

只有与当前图片 SHA256 对应、由允许的审核人创建的批准记录能进入 ZIP。撤回/驳回新增一条审核事件，保留历史。已看见的审核事件被编辑或删除会阻塞交付。

最终交付记录同时列出目标候选数、已生成数和实际交付数。6 个候选通过 2 个时只能说交付 2 张，不会复制凑到 6 张。

## 平台触发方式

飞书保存已提交任务，独立单机 Runner 按冻结请求推进确定性步骤并保存账本；遇到原生生图节点时停在 `waiting_worker`，由当前获授权的 Codex 会话领取一次派发并提交真实输出。Codex 不长期控制任务队列，也不能在离线时伪装能自动调用原生工具。额度不足、电脑睡眠或原生工具不可用时保留等待状态和账本，恢复后由 Runner 对账继续。

Human UI 只承担本人审图及查看交付；审核写入必须走 Engine API。若未来需要飞书按钮真正触发全天队列，再增加常驻服务、服务身份、分布式领取任务和稳定 Producer API。不要用浏览器 Cookie 自动化伪装 API。
